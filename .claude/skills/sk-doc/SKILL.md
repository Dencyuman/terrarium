# Doc - ドキュメント整合性チェック & 修正

## 使用方法

```
/sk-doc check [path]                              # チェックのみ
/sk-doc fix [path] [critical|high|all]  # チェック → 修正
```

- `check`: ドキュメントと実装の整合性をチェック（read-only、デフォルト）
- `fix`: チェック後に修正計画を立てて実行
- `path`: 対象ファイル/ディレクトリ（省略時はプロジェクト全体）
- `[critical|high|all]`: 修正対象の重要度（`fix` 時のみ、デフォルト: high 以上）

ARGUMENTS: $ARGUMENTS

---

## check モード

### 動作フロー

1. **発見**: Markdown ファイルとソースコードファイルを収集
2. **分析**: ドキュメント記述と実装を照合
3. **検証**: コメント、構造、コマンド、パターンの整合性を確認
4. **評価**: コンテキストエンジニアリングの品質を評価
5. **レポート**: 重要度別に発見事項を報告

### チェック項目

#### 1. ドキュメント-実装整合性

- ディレクトリ構造の一致
- ファイル命名規則の遵守
- コマンド/スクリプトの実行可能性
- コード例の正確性
- 依存関係の最新性
- 環境変数/設定の正確性

#### 2. コメント品質

- docstring/JSDoc の存在と正確性
- インラインコメントと実装の一致
- TODO/FIXME/HACK の未解決検出
- コメントアウトコード（削除候補）
- 古い・無効なコメントの検出

#### 3. コンテキストエンジニアリング

- 必須ドキュメントの存在確認
- AI 可読性の評価
- 構造化の程度（テーブル、リスト、チェックリスト）
- 重複・矛盾の検出

### 出力形式

```markdown
## ドキュメント整合性チェック結果

### 重大な問題（即修正推奨）
- **ファイル**: path:行番号
- **問題**: 説明
- **影響**: 影響範囲
- **推奨**: 修正方法

### 改善推奨（中優先度）
...

### 良好な点
...

### コンテキストエンジニアリング評価
...
```

## fix モード

### 動作フロー

1. **チェック実行**: 上記 `check` モードと同じチェックを実行
2. **判断**: 各問題について修正対象を判定（ドキュメント / 実装 / 両方）
3. **計画**: 修正タスクに分割し、優先順位付け
4. **提示**: 修正計画をユーザーに提示
5. **確認**: 重要な修正はユーザー承認、軽微なものは自動実行
6. **実行**: 承認された修正を実行
7. **検証**: 修正後の整合性を確認
8. **レポート**: 実施内容と結果を報告

### 修正対象の判断ロジック

1. **明らかに古い情報**: ドキュメントを自動更新（存在しないコマンド、変更された構造）
2. **git 履歴から判断**: 最近変更された方が正しい可能性高
3. **実装の制約**: 実装側の制約がある場合はドキュメントを修正
4. **判断困難**: ユーザーに確認

### 修正の重要度分類

- **Critical**: 即座に修正すべき（実行不可コマンド、存在しない構造）
- **High**: 早期修正推奨（不正確な説明、古いパターン）
- **Medium**: 改善推奨（軽微な不一致、補足不足）
- **Low**: 任意（スタイル、表現の改善）

### 自動実行の基準

以下は自動実行（ユーザー確認不要）:

- 明らかに古いコマンド/パスの修正
- 6ヶ月以上前の古い TODO/FIXME 削除
- タイポ修正

以下はユーザー確認必須:

- コメントアウトコード削除
- 実装パターンの変更
- 判断が困難な不一致
- 重要なアーキテクチャ変更

---

## 境界

**実施すること:**

- ドキュメントと実装の徹底的な整合性チェック
- コードコメントの品質と正確性の検証
- TODO/FIXME/コメントアウトコードの検出
- `fix` 時: 修正計画作成、承認後の修正実行

**実施しないこと:**

- `check` モードでのコード変更
- ユーザー承認なしでの重要な修正（`fix` モード）
- 外部リンクの有効性チェック
- コードの機能的な正確性テスト

# Task Make - Issue 分析 & ローカル実装プラン生成

## トリガー

- GitHub Issue の実装に着手する前に、コードベースを調査して実装プランを立てたい
- Issue の内容とコードの現状を照らし合わせた TODO 付きプランが欲しい
- チーム内で共有しないローカルな作業メモとして残したい

## 使用方法

```
/sk-task-make [Issue URL or 番号]
```

引数:

- `Issue URL`: GitHub Issue の URL（例: `https://github.com/dencyuinc/databuddy/issues/175`）
- `Issue 番号`: Issue 番号のみ（例: `175`）。省略時は対話で聞く

ARGUMENTS: $ARGUMENTS

## 動作フロー

1. **Issue 取得**: `gh issue view` で Issue のタイトル・本文・ラベルを取得する
2. **コードベース調査**: Issue の内容から関連するコードを Glob / Grep / Read で調査する
3. **プラン生成**: 調査結果を踏まえた実装プランを生成する
4. **ユーザー確認**: 生成したプランを提示し、修正依頼があれば反映して再提示する
5. **ファイル保存**: 承認後、`tasks/` ディレクトリにプランファイルを保存する
6. **完了報告**: 保存先パスを表示する

## ステップ詳細

### 1. Issue 取得

引数から Issue 番号を特定する。URL が渡された場合は番号部分を抽出する。

```bash
gh issue view <番号> --repo dencyuinc/databuddy --json number,title,body,labels
```

取得する情報:

- Issue 番号・タイトル
- Issue 本文（提案内容、背景、影響範囲など）
- ラベル（enhancement / bug 等）

### 2. コードベース調査

Issue の内容から以下を調査する:

- **対象ファイルの特定**: Issue 本文で言及されているファイルパス、コンポーネント名、関数名を Glob / Grep で検索
- **現状の実装把握**: 対象ファイルを Read で読み込み、現在のコード構造・型定義・依存関係を把握
- **関連コードの探索**: 対象コンポーネントの呼び出し元、共通ユーティリティ、再利用可能な既存実装を調査
- **API エンドポイント**: 関連する API ルートがあれば確認

調査は **十分な深さ** で行う。表面的なファイル一覧ではなく、実装に必要な以下の情報を収集する:

- 変更対象ファイルの現在のソースコード
- 型定義（Props / Interface / Schema）
- 呼び出し元と影響範囲
- 再利用できる既存コンポーネント・ユーティリティ・スタイル
- 既存の命名規則・コード規約

### 3. プラン生成

以下のテンプレートに沿ってプランを生成する。**ブランチ名は `git branch --show-current` で自動取得してメタデータに含める。**

```markdown
---
issue: <番号>
branch: <現在のブランチ名>
---

# Issue #<番号>: <タイトル>

## Context

[なぜこの変更が必要か。Issue の背景・課題・目的を簡潔にまとめる]

## 調査結果

### 現状の実装
[調査で把握した現在のコード構造の要点]

### 再利用できる既存リソース
[既存コンポーネント、ユーティリティ、API、スタイルなど。ファイルパス付き]

## 実装プラン

### Step 1: [ステップ名]
- **対象**: [新規作成 or 変更するファイルパス]
- **内容**: [具体的な変更内容]

### Step 2: ...
[必要なステップ数だけ繰り返す]

## 変更ファイル一覧

| ファイル | 変更種別 | 内容 |
|---------|---------|------|
| `path/to/file` | 新規 / 変更 | 概要 |

## エッジケース・注意点

- [後方互換性、既存データへの影響、パフォーマンス等]

## TODO

- [ ] Step 1: [ステップ名]
- [ ] Step 2: [ステップ名]
- [ ] ...
- [ ] lint / format チェック
- [ ] 動作確認

## 検証方法

[手動確認手順、テスト方法など]
```

**プラン生成のルール:**

- **ファイル先頭に YAML frontmatter で `issue` と `branch` を必ず記録する**
- 各ステップは具体的なファイルパスと変更内容を含める
- 再利用できる既存コードがあれば積極的に参照する（新規作成より既存活用を優先）
- TODO リストは実装の順序に沿った粒度で作成する（チェックボックス形式）
- エッジケースは Issue 本文で言及されているものに加え、調査で発見したものも含める

### 4. ユーザー確認

生成したプランを提示し、確認を求める:

```
## プラン プレビュー

[プラン全文]

---

この内容で tasks/ に保存してよいですか？修正があれば指示してください。
```

修正依頼があった場合:

- 指摘箇所を修正して再度プレビューを提示する
- 承認されるまで繰り返す

### 5. ファイル保存

承認後、`tasks/` ディレクトリにファイルを保存する。

#### ファイル命名規則

```
tasks/<連番>.<日本語タスク名>.md
```

- **連番**: `tasks/` 内の既存ファイルから最大番号を取得し +1 する。ファイルが存在しない場合は `1` から開始
- **タスク名**: Issue タイトルから生成。日本語のまま簡潔にまとめる。長すぎる場合は要点のみに短縮（最大40文字程度）

例:

```
tasks/1.チャットファイル添付チップUI刷新.md
tasks/2.スケジュールリトライ機能追加.md
tasks/3.ログインリダイレクト修正.md
```

#### 連番の取得方法

```bash
# tasks/ ディレクトリが存在しなければ作成
mkdir -p tasks

# 最大番号を取得（結果が空の場合は呼び出し元で 0 として扱う）
ls tasks/*.md 2>/dev/null | sed 's/.*\///' | sed 's/\..*//' | sort -n | tail -1
```

#### ディレクトリについて

- `tasks/` は `.gitignore` に含まれており、Git 管理外のローカル作業用ディレクトリ
- チームへの共有が不要なローカルな実装メモ・進捗管理として使用する

### 6. 完了報告

```
✅ 実装プランを保存しました

- ファイル: tasks/<連番>.<slug>.md
- Issue: #<番号> <タイトル>
- ブランチ: <ブランチ名>
- TODO: <N> 項目
```

## ツール連携

- **Bash**: gh issue view, mkdir, ls（連番取得）, git branch --show-current
- **Glob**: 関連ファイルの探索
- **Grep**: キーワードでのコード検索
- **Read**: ソースコードの内容確認
- **Write**: プランファイルの保存

## TODO の運用

プラン内の TODO リストは、実装の進捗管理に使用する:

- 各ステップの完了時にチェックを入れる（`- [ ]` → `- [x]`）
- 実装中に新たな TODO が見つかった場合は追記する
- 全 TODO が完了したら、プランファイルの冒頭に `**Status: Done**` を追記する

## 境界

**実施すること:**

- GitHub Issue の内容取得と分析
- 関連コードベースの調査（十分な深さで）
- 実装プラン・TODO リストの生成
- ブランチ名の自動記録（frontmatter の `branch` フィールド）
- ユーザー承認を得てからのファイル保存
- `tasks/` ディレクトリの作成（存在しない場合）

**実施しないこと:**

- ユーザーの承認なしでプランファイルを保存
- コードの実装や修正（プラン作成のみ）
- ブランチの作成やコミット
- `tasks/` ディレクトリの Git 追跡（.gitignore 済み）
- 既存プランファイルの上書き（同一 Issue でも新しい連番で作成）

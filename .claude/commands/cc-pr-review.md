# /cc:pr-review - プルリクエストレビュー

## トリガー

- PRのコードレビューを依頼された
- マージ前にコード品質を確認したい
- 他メンバーのPRをレビューしたい

## 使用方法

```
/cc:pr-review [PR番号またはURL]
```

引数:

- `PR番号またはURL`: レビュー対象のPR（省略時は現在のブランチのPR）

## 動作フロー

1. **PR取得**: `gh pr view` でPR情報とdiffを取得
2. **分析**: 変更内容をコード品質・セキュリティ・パフォーマンスの観点で分析
3. **コード読み込み**: 変更ファイルの前後コンテキストを `Read` で確認
4. **レビュー**: 問題点・改善提案・良い点をまとめる
5. **レポート**: 重要度別にレビュー結果を提示

主要な動作:

- PR の diff を取得して全変更ファイルを分析
- 変更ファイルの周辺コードも読み込んで文脈を把握
- コード品質・セキュリティ・パフォーマンス・保守性の観点でレビュー
- 重要度別に問題点を整理して提示

## ツール連携

- **Bash**: gh pr view, gh pr diff の実行
- **Read**: 変更ファイルの詳細読み込み（前後コンテキスト含む）
- **Grep/Glob**: 関連コードの検索、影響範囲の調査

## 主要パターン

### レビュー観点

- **品質**: コードの可読性、命名、責務分離、重複
- **セキュリティ**: インジェクション、認証・認可、入力バリデーション
- **パフォーマンス**: N+1クエリ、不要な再レンダリング、メモリリーク
- **保守性**: テスタビリティ、拡張性、依存関係
- **プロジェクト規約**: 既存パターンとの一貫性

### レビューの深さ

- 変更行だけでなく、変更ファイルの全体的なコンテキストを確認
- 関連するファイル（呼び出し元/先）も必要に応じて確認
- DB スキーマ変更がある場合はマイグレーションの妥当性も確認

## 例

### 現在のブランチのPRをレビュー

```
/cc:pr-review
# 現在のブランチに紐づくPRを自動検出
# diff を分析してレビュー結果を提示
```

### PR番号を指定してレビュー

```
/cc:pr-review 150
# gh pr view 150 でPR情報取得
# gh pr diff 150 で変更内容取得
# レビュー結果を提示
```

## 出力形式

```markdown
## PRレビュー結果

**PR**: #150 - タイトル
**変更**: +XX / -YY (NN files)

### 🔴 要修正

- **ファイル**: application/app/api/route.ts:45
  - **問題**: SQLクエリにユーザー入力が直接埋め込まれている
  - **提案**: パラメータバインディングを使用する

### 🟡 改善提案

- **ファイル**: application/components/DataTable.tsx:78
  - **問題**: useEffect内でstateを更新しており無限ループの可能性
  - **提案**: 依存配列を見直すか useMemo に変更

### 🟢 良い点

- RLS を正しく適用している
- エラーハンドリングが適切
- 型安全性が確保されている

### 📋 確認事項

- [ ] マイグレーションの実行順序
- [ ] 既存データへの影響
```

## 境界

**実施すること:**

- PR の変更内容を多角的にレビュー
- 問題点と改善提案を重要度別に整理して提示
- 変更の周辺コンテキストを考慮した深いレビュー

**実施しないこと:**

- PR へのコメント投稿（レビュー結果はユーザーに提示のみ）
- コードの自動修正（cc:improve で実施）
- PR の approve / request changes（ユーザーが判断）

# /cc:doc-sync - ドキュメント同期修正

## トリガー

- cc:doc-check で検出された問題を修正したい
- ドキュメントと実装の不一致を解消したい
- 古いコメントやコメントアウトコードを整理したい

## 使用方法

```

/cc:doc-sync [--check-first] [--severity critical|high|medium|all]

```

オプション:

- `--check-first`: 最初に cc:doc-check を実行してから修正
- `--severity`: 修正対象の重要度（デフォルト: high以上）

## 動作フロー

1. **分析**: cc:doc-check の結果を読み込み（または実行）
2. **判断**: 各問題について修正対象を判定（ドキュメント/実装/両方）
3. **計画**: 修正タスクに分割し、優先順位付け
4. **提示**: 修正計画をユーザーに提示
5. **確認**: 重要な修正はユーザー承認、軽微なものは自動実行
6. **実行**: 承認された修正を実行
7. **検証**: 修正後の整合性を確認
8. **レポート**: 実施内容と結果を報告

主要な動作:

- cc:doc-check の結果を基にした修正計画作成
- ドキュメント/実装のどちらを修正すべきか判断
- タスク分割と優先順位付け
- 重要度に応じた確認フロー
- git履歴やコンテキストからの推測

## ツール連携

- **Read**: ドキュメントとコードの詳細読み込み
- **Edit**: ファイルの修正
- **Bash**: git log で変更履歴確認、コマンド検証
- **Glob/Grep**: 関連ファイルの検索と分析

## 主要パターン

### 修正対象の判断ロジック

1. **明らかに古い情報**: ドキュメントを自動更新
  - 例: 存在しないコマンド、変更された構造
2. **git履歴から判断**: 最近変更された方が正しい可能性高
3. **実装の制約**: 実装側の制約がある場合はドキュメントを修正
4. **判断困難**: ユーザーに確認
  - 実装者がドキュメントを知らなかった可能性
  - ドキュメント通りに実装できなかった可能性

### 修正の重要度分類

- **🔴 Critical**: 即座に修正すべき（実行不可コマンド、存在しない構造）
- **🟡 High**: 早期修正推奨（不正確な説明、古いパターン）
- **🟢 Medium**: 改善推奨（軽微な不一致、補足不足）
- **⚪ Low**: 任意（スタイル、表現の改善）

### タスク分割の基準

- ファイル単位
- 問題の種類（構造/コマンド/コメント）
- 影響範囲（Backend/Frontend/Infrastructure）

## 例

### cc:doc-check の結果から修正

```

/cc:doc-sync

# 前回の cc:doc-check 結果を読み込み

# 修正計画を作成して提示

# ユーザー承認後に修正実行

```

### チェックと修正を一括実行

```

/cc:doc-sync --check-first

# cc:doc-check を実行

# 検出された問題の修正計画を作成

# 修正実行

```

### 重大な問題のみ修正

```

/cc:doc-sync --severity critical

# 🔴 Critical の問題のみを修正対象

# 実行不可コマンドや存在しない構造を優先修正

```

## 自動実行の基準

以下は自動実行（ユーザー確認不要）:

- 明らかに古いコマンド/パスの修正
- 6ヶ月以上前の古いTODO/FIXME削除
- タイポ修正
- リンク切れ修正

以下はユーザー確認必須:

- コメントアウトコード削除
- 実装パターンの変更
- 判断が困難な不一致
- 重要なアーキテクチャ変更

## 境界

**実施すること:**

- cc:doc-check の結果を基にした修正計画作成
- ドキュメント/実装のどちらを修正すべきか判断
- タスク分割と優先順位付け
- 重要度に応じた確認フローの実行
- 修正の実行と検証

**実施しないこと:**

- ユーザー承認なしで重要な修正を実行
- 判断根拠が不明確な修正を強行
- 動作テストなしで実装を変更
- バックアップなしで大規模修正

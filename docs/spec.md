# Terrarium — v0.1 要件定義書

## 1. 背景

### 1.1 プロジェクトの出発点

2026年4月、XにおけるあるポストがTerrariumの着想の源となった。ユーザー「デスクロ」氏が古いノートPCでローカルLLM(Gemma 4)を用いてAI生物100体を集団生活させる「神様ごっこ」を行ったところ、集団の中で自発的にルールが設定され、リーダー(または神)の選出までが実行された、という観察報告である。

この観察は単なる娯楽エピソードを超えて、いくつかの重要な問いを投げかけている。

- LLMベースの自律エージェントを多数並列に走らせたとき、どのような社会的創発が発生するのか
- 制度、規範、リーダーシップといった概念は、事前に与えられなくても自発的に生まれうるのか
- 既存の社会シミュレーション研究(Stanford Smallville, AI Town, Project Sid等)と何が違いうるのか
- 世代を重ねたとき、何が残り何が失われ、何が変質していくのか

Terrariumは、これらの問いに対する「観察装置」として構想された、個人による趣味OSS/商用プロジェクトである。

### 1.2 既存プロジェクトとの位置づけ

社会シミュレーション領域には既に複数の系譜が存在する。

**疫病/戦争シミュレーションの系譜**(統計的予測を目的とする)
Kermack-McKendrick以来の compartmental model (SIR/SEIR) と、Covasim等に代表される確率的 Agent-Based Model が主流。エージェントは有限状態機械で駆動され、政策判断を目的として国家規模(100万〜1000万エージェント)で回される。個人の内面はモデル化されない。

**LLMベース社会シミュレーションの系譜**(創発の観察を目的とする)
Stanford Smallville (2023)、AI Town、Project Sid、Microverse (KsanaDock, 2025)等。LLMが各エージェントの意思決定を担い、自然言語で相互作用する。規模は10〜100体程度。ただし多くは「既に完成した社会構造(オフィス、町、学校)の中でAIキャラクターが生活する」というフォーマットを採用しており、社会構造そのものの発生過程は観察対象外となっている。

**Terrariumの独自ポジション**
Terrariumは、上記いずれとも異なる「**制度が自発的に立ち上がる瞬間**を観察するためのハーネス」を目指す。事前定義された役職、法律、通貨、関係性を最小化し、物理的に可能な行為のみをエージェントに許す。結婚、通貨、階級、規範といった概念は、エージェントが自ら発見し、命名し、共有オブジェクトとして物体化していく過程そのものが観察対象となる。

これは実装上の思想として「**ハーネスは『できること』を提供するだけで、『すべきこと』は何も提供しない**」と表現される。

### 1.3 プロジェクトの性格

- **個人による趣味プロジェクト**であり、本業(株式会社DENCYU / DataBuddy)とは完全に独立して運営される
- **OSS公開は行わず、プライベート開発**とする。将来的な商用配布(Steam)を想定
- **作者自身が最初のユーザー**である。作者が観察して面白いと感じるものを作る、という基準が最優先される
- **放置ゲームとしての体験**を主軸に据える。作業PCの裏でシミュレーションが進行し、ユーザーは要所で観察する
- 将来的に、自宅PCで走るシミュレーションの状態をクラウド経由でスマートフォンから閲覧する構成(OpenClaw的運用)への拡張を視野に入れる
- 将来的に、Steamでの買い切り販売($10〜$15 / ¥1,500程度)による「バズ + 小遣い」程度の収益化を想定

## 2. プロダクトコンセプト

### 2.1 プロダクト名

**Terrarium**

- 語源: 生物学/自然観察文化における「ガラス箱の生態系」
- 意味の含意: 観察者は手を出さず、ガラス越しに内部の世界を眺める
- プロダクトのメタファーとして完全に一致する

### 2.2 ポジショニング

- ❌ AI操作サンドボックスゲーム
- ❌ リアルタイム操作型の神ゲーム(Populous / Black & White 系の、神が世界を直接操作して進めるゲーム)
- ❌ ユーザーを世界内の一プレイヤー/NPC として置き、世界の中から介入する形式(既存 LLM 社会シムの大半がこれに該当)
- ⭕ **放置型AI社会ドキュメンタリー**
- ⭕ **AI文明の盆栽**
- ⭕ **神のテラリウム** — ユーザーは世界の外側に立つ神である。ガラス箱の中の社会を眺める観察者としての神であり、博物学者/研究者ではない
- ⭕ v0.1 では介入手段を持たず純粋な観察のみ。v0.2 以降で「試練を与える」等の**神としての介入手段**を追加予定。介入は世界の外側からの働きかけ(天変地異、試練、啓示等)として設計し、世界内の登場人物として振る舞う形式は採らない

### 2.3 ユーザー体験の設計原則

- **v0.1 は介入しない**: ユーザーは初期条件を設定した後、観察のみを行う。世界への介入機能は v0.1 では持たない(v0.2 以降で神としての介入手段を追加予定。ただし v0.1 の動作検証期間中は純粋な観察専用とする)
- **放置される**: シミュレーションは裏で進行し、ユーザーは好きなタイミングで覗く
- **再現可能**: 同一の初期条件と乱数シードから、同一の展開が再生される(LLMサンプリングのseed固定を含む)
- **物語が残る**: シミュレーション終了後、そこで起きた出来事が時系列ログ・関係性グラフ・家系図として閲覧できる
- **スクリーンショット映えする**: SNS投稿に適した画面構成。特定の瞬間(リーダー選出、世代交代、新規共有オブジェクトの生成)が明示的に記録される

## 3. v0.1 スコープ

### 3.1 v0.1のゴール

**「20体のAIエージェントが世代を重ねながら自律的に行動し、関係性・文化継承・共有オブジェクトを通じて規範や役割の萌芽が観察される、観察専用プロトタイプ」を動作する状態で完成させる。**

v0.1は作者の検証用として閉じており、UI/UX・ビジュアル・パフォーマンスの作り込みは最小限とする。

### 3.2 スコープに含むもの(In Scope)

#### 3.2.1 世界 (World)

- 2Dグリッド、20×20マス、固定サイズ
- 地形タイル4種: 草地 / 水域 / 森 / 岩場
- リソース: 食料(果実・獲物等)が地形ごとに確率生成、時間経過で再生
- 固定マップ1種のみ、地形は乱数シードで生成するが v0.1 ではシードをハードコード
- エージェント間の視界は半径3マス以内

#### 3.2.2 エージェント (Agent)

- 初期個体数: 20体(性別比は概ね1:1、年齢は繁殖可能な成人期に集中させる)
- 動的に増減する(誕生/死亡)
- 保持する状態:
  - 位置、年齢、空腹度、体力
  - 性別、名前、簡易性格タグ(協調/攻撃/好奇 の3軸、各0-100)
  - 他エージェントごとの関係データ(好感度、信頼度、関係タイプ)
  - ローリングログ(直近20件のイベント記憶)
  - 日次サマリ(LLMによる記憶圧縮、日ごとに蓄積)

#### 3.2.3 アクション空間 (Actions)

物理的に可能な基本動詞のみを提供し、社会的な意味づけ(結婚、窃盗、裁判等)はエージェントの解釈と命名に委ねる。

- `move(direction)`
- `speak(text, listeners)`
- `take(object)`
- `give(object, agent)`
- `attack(agent)`
- `embrace(agent)`
- `teach(agent, memory_id)`
- `reproduce_with(agent)` ← 双方の合意が必要
- `create_shared_object(content)`
- `modify_object(object_id, new_content)`
- `wait`

#### 3.2.4 ライフサイクル

- 加齢: 1 game-day = N tick(初期値 N=10 を想定、要チューニング)
- 寿命: 老衰による確率的死亡、飢餓による死亡、他エージェントからの致命的な attack による死亡
- 生殖: `reproduce_with` の相互合意成立 → 子エージェントの出生
- 子の性格: 両親の性格タグの平均 + 確率的変異
- 教育: `teach` により親の記憶の一部が子に転送される。転送時に確率的な変質が発生する(伝言ゲーム的ノイズ)
- 死亡時: 本人の記憶は消失。所持物はその場に残留し、他エージェントが `take` 可能

#### 3.2.5 共有オブジェクト

- 世界に存在する「書き物」のメタファー
- 任意のエージェントが `create_shared_object` で作成可能
- 視界内の他エージェントが観測・`modify_object` で編集可能
- ハーネスは「これは掟である」「これは歴史書である」といった意味づけを一切与えない。エージェント側の解釈に委ねる

#### 3.2.6 スケジューラ (Scheduler)

- tick制、lockstep
- 3フェーズ構造:
  1. **Observe**: 全エージェントが世界状態を観測
  2. **Decide**: 全エージェントが並列にLLM呼び出しで意思決定
  3. **Commit**: 全アクションを一括適用、衝突は agent_id 順で解決
- Decide フェーズ中の世界状態は不変(同tick内で他者の行動は観測されない、次tickで反映)
- LLM並列呼び出しはセマフォで制御(初期値 4並列、チューニング対象)

#### 3.2.7 LLM統合

- バックエンド: Ollama(`localhost:11434`)
- モデル: `gemma3:4b` をデフォルトとする。設定ファイルで差し替え可能とする
- 通信: Godot の HTTPRequest ノードから直接叩く(v0.1ではPythonサイドカーは設けない)
- レスポンス形式: structured output (JSON) を指示
- フォールバック: JSON parse 失敗 / タイムアウト(30秒) / HTTP エラー時は `wait` として扱う
- プロンプトには現在状態を構造化して注入する。LLMの内部記憶に依存しない設計とする

#### 3.2.8 観察レイヤー (神視点の分析)

エージェントからは見えない、観察者専用のビュー。

- **関係性グラフ**: 発話・相互作用ログから、誰が誰をどう認識しているかを可視化
- **イベントタイムライン**: 重大イベント(出生/死亡/殺害/結合/共有オブジェクト生成/子への教育)の時系列表示
- **家系図**: 世代関係の可視化
- **エージェント詳細ビュー**: 個別の現在状態・記憶・関係・子孫を表示

#### 3.2.9 UI

- Godot デスクトップアプリケーション
- メイン画面:
  - 中央: 2Dグリッドの世界ビュー(タイル + エージェントアイコン)
  - 右パネル: 発話ログ(最新N件、スクロール可能)
  - 下パネル: 再生コントロール(一時停止/再開、速度 1x/2x/5x、リセット)
  - 画面上部ステータス: 現在tick / 現在日 / 現在人口 / 最高世代数
- タブ切り替え: 世界ビュー / 関係性グラフ / 家系図 / イベントタイムライン
- エージェントクリックで詳細ウィンドウ表示

#### 3.2.10 初期条件

- v0.1 ではハードコード固定
- 20体、乱数シードから名前リストより選出、性格は3軸それぞれ正規分布
- 性別比 1:1、年齢は成人期に偏った分布
- 地形生成シードも固定

### 3.3 スコープに含まないもの(Out of Scope)

以下は v0.2 以降とし、v0.1 では一切実装しない。

- 複数シナリオ(中世村、会社、宇宙船、無人島等)
- 初期条件の GUI 編集
- シナリオ定義ファイルの外部入力(YAML/JSON)
- 先読み/バッファリング機構
- タイムラプス再生
- ハイライト自動検出 / 帰宅時サマリー生成
- セーブ/ロード
- クラウド同期 / スマートフォン閲覧
- Discord webhook 等の外部通知
- マップサイズの動的変更
- 地形の動的変化(気候/災害)
- 複数集落/地理的隔離による文化分岐
- 言語の分化
- 明示的な「法」「通貨」「職業」のデータ型(共有オブジェクト経由での自発的出現のみ扱う)

### 3.4 成功条件 (Definition of Done)

以下すべてを満たした時点で v0.1.0 完成とする。

1. アプリケーション起動時に、マップと20体のエージェントが描画される
2. 「開始」操作によりtickが進行する
3. エージェントが移動し、食料を取得し、相互に発話する
4. 発話内容がログパネルにリアルタイムで流れる
5. 一時停止 / 速度変更 / リセット が機能する
6. エージェントが加齢し、死亡し、新たに誕生するサイクルが観測できる
7. 少なくとも1世代以上の世代交代が30分以内のプレイで観測可能である
8. 少なくとも1つ以上の共有オブジェクトがエージェントにより自発的に生成される事例がプレイ中に観測可能である
9. 100 tick 以上動作してもアプリケーションがクラッシュしない、エージェントが無限ループに陥らない
10. 同一シードで起動した場合、LLMサンプリングの非決定性を除いて同一の初期状態から始まる

## 4. 技術選定

### 4.1 確定事項

| 領域 | 選定 |
|---|---|
| ゲームエンジン | Godot 4 (最新安定版) |
| 主言語 | GDScript |
| LLM バックエンド | Ollama (ローカル) |
| デフォルトモデル | gemma3:4b |
| LLM 通信 | Godot 標準 HTTPRequest ノード |
| 永続化 | なし(v0.1 はインメモリのみ) |
| 配布形式 | v0.1 はソースのみ(作者自身のローカル実行) |
| OSS ライセンス | 未定(v0.1 は Private リポジトリ、公開しない) |
| プラットフォーム | v0.1 は開発機 (macOS or Linux) のみ想定 |

### 4.2 Python サイドカーについて

v0.1 では Python サイドカー(FastAPI 等)は導入しない。Godot から Ollama を直接叩く最小構成で進める。

以下の条件に該当した場合、v0.2 以降で導入を検討する。

- GDScript の非同期制御で並列LLM呼び出しが破綻する場合
- Python エコシステム固有のツール(プロンプト管理、トレーシング等)が必要になった場合
- 将来的なモバイル版で、サーバーサイドを分離した構成が必要になった場合

### 4.3 将来の拡張計画(参考)

v0.2 以降で想定する技術拡張。

- Cloudflare R2 への状態スナップショット定期アップロード(スマートフォン閲覧用)
- Cloudflare Pages 上の軽量 Web UI(PWA対応)
- Discord webhook による重大イベント通知
- Steam Direct 経由での商用配布
- 複数シナリオおよびシナリオ定義ファイル(YAML)の外部入力
- モバイル版 Godot ビルド(Android / iOS)

## 5. 実装計画

### 5.1 Phase 分割

v0.1 は以下の Phase に分割して段階的に実装する。各 Phase 完了時に動作確認とコミットを行う。

#### Phase 1: 静的基盤 (v0.1.0-phase1)

1. Godot プロジェクトの初期化、リポジトリ設定
2. World(グリッド + タイル描画、静的)
3. Agent(ドット/スプライト表示、静的配置)
4. UI 骨格(ログパネル、コントロールパネル、タブ切り替えの枠)

**確認事項**: マップと20体が描画される、UI 要素が配置されている。

#### Phase 2: tick 進行とローカル行動 (v0.1.0-phase2)

5. Scheduler(tick 駆動、3フェーズ構造、ただし Decide はローカルロジック)
6. Action 基盤(`move`, `wait`)
7. リソース機構(食料の生成/消費、再生)
8. 空腹度/体力の状態遷移

**確認事項**: LLM なしでエージェントがランダム移動し、食料を取得し、空腹で減衰する。

#### Phase 3: LLM 統合 (v0.1.0-phase3)

9. Ollama クライアント (HTTPRequest ベース)
10. プロンプトビルダー、レスポンスパーサ
11. LLM ベースの decide、フォールバック処理
12. 並列制御(セマフォ)

**確認事項**: LLM が意思決定する、発話が出る、20体並列で動作する。

#### Phase 4: 社会の芽 (v0.1.0-phase4)

13. `speak(to)` によるエージェント間対話
14. 関係性データ構造、好感度/信頼度の更新
15. `take` / `give` による物品のやり取り
16. `attack` / `embrace` による身体的相互作用
17. 関係性グラフ UI

**確認事項**: エージェント同士が会話し、関係が変化し、グラフに反映される。

#### Phase 5: ライフサイクル (v0.1.0-phase5)

18. 加齢システム、日の概念
19. 死亡処理(老衰/飢餓/殺害)
20. `reproduce_with`(合意ベースの生殖)
21. 子エージェント生成、性格継承
22. 家系図 UI

**確認事項**: エージェントが死亡・誕生し、世代が進行する。

#### Phase 6: 文化継承 (v0.1.0-phase6)

23. 日次サマリ生成(LLM による記憶圧縮)
24. `teach` アクション(記憶の部分転送)
25. 伝承時の変質機構

**確認事項**: 親の記憶の一部が子に継承され、世代を超えて変質する。

#### Phase 7: 共有オブジェクトと制度の器 (v0.1.0-phase7)

26. 共有オブジェクトのデータ構造
27. `create_shared_object`, `modify_object`
28. 視界内の共有オブジェクトの観測機構
29. イベントタイムライン UI

**確認事項**: エージェントが「書き物」を作成し、他者が観測・編集可能になる。

#### Phase 8: 統合調整 (v0.1.0)

30. 全機能の統合テスト
31. プロンプトチューニング
32. UI微調整、アイコン・アニメーション
33. パフォーマンス調整

**確認事項**: 「3.4 成功条件」全項目を満たす。

```
    └── config.json           ← LLMエンドポイント、モデル名等
```

## 6. 技術的な論点と設計判断

### 6.1 決定論性について

v0.1 は「同じシードから同じ展開が再生される」を目指すが、LLM のサンプリングの非決定性により完全な再現性は保証されない。以下の方針で最大限近づける。

- 世界側の乱数(地形生成、リソース再生、加齢判定、変異等)は固定シードから派生
- LLM 呼び出しには temperature = 0 を試行(決定論性優先)、ただし創発が貧弱な場合は 0.3 程度に引き上げて試す
- LLM のレスポンスをログに記録し、後から同じシミュレーションを再生可能にする(Phase 8 で検討、v0.2 で本実装)

### 6.2 Gemma 3 4B の能力限界への対処

4B モデルで「世代継承、制度発生、複雑な社会文脈」を期待するのは楽観的である可能性が高い。以下で緩和する。

- プロンプトは可能な限り短く、状態は構造化して渡す
- 長文理解を要する文脈(3世代前の祖父の記憶、部族の掟の全文)は最初から与えず、エージェントの能動的な想起(`remember` / `teach` の伝達チェーン)に委ねる
- 設定ファイルで `gemma3:12b`, `qwen3:8b` 等への差し替えを容易にする
- プロンプトチューニング(Phase 8)で現実的な挙動を引き出す

### 6.3 創発の観察可能性

「リーダー選出」「規範形成」「新宗教の発生」等の観察したい現象が、v0.1 の 30分〜数時間プレイで本当に発生するかは未知である。以下の前提で設計する。

- v0.1 はあくまで「観察のためのハーネスが機能すること」を検証する段階
- 観察したい現象が発生しなかった場合、それ自体がハーネス設計の改善ネタとなる
- 発生しやすさの調整は、アクションコストや資源希少性のパラメータチューニングで行う(v0.1 完成後)

### 6.4 パフォーマンス

- 20体 × 各 tick で LLM 呼び出し。Gemma 3 4B は Apple Silicon Mac で 1体あたり 1〜3 秒を想定
- 並列 4 本のセマフォ制御で、1 tick あたり 10〜20 秒程度と見積もる
- ゲーム内時間の進行速度は「作業中裏で数時間走らせれば1日進む」程度のオーダー感
- この速度感は放置ゲームとしては適切と判断する

## 7. 用語集

| 用語 | 定義 |
|---|---|
| tick | シミュレーションの最小時間単位 |
| day(日) | N tick で構成される上位時間単位。日次サマリはこの単位で生成される |
| 世代 | ある親から生まれた子らのまとまり。家系図の階層を示す |
| 観察レイヤー | エージェントからは見えない、観察者(ユーザー)専用の分析表示 |
| 共有オブジェクト | 世界に物体として存在する「書き物」。エージェントが作成・編集可能 |
| 日次サマリ | 各エージェントが1日の記憶をLLMで圧縮したテキスト |
| ハーネス | シミュレーションの基盤。ルールではなく可能性だけを定義する |
| 創発 | 個々のルールに明示されていないのに、集団レベルで現れる秩序や現象 |
